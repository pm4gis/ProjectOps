# Core model overview

ProjectOps is a connected operating model for delivering change. It is designed to keep intent, work, readiness, and outcomes linked from start to finish, without relying on heavy documentation.

ProjectOps is not a tool. It can be used across tools. It is not a single project methodology. It can sit across agile, waterfall, stage-gate, or a hybrid.

## The five practices

ProjectOps is organised into five practices that run together:

1. **PlanningOps**: prioritisation, scope boundaries, sequencing, dependencies, and decision points  
2. **BuildOps**: delivery flow, quality controls, release readiness, and operational safety  
3. **ChangeOps**: stakeholder alignment, readiness, training, communications, and early-life support  
4. **ValueOps**: outcomes, baselines, benefit ownership, measurement, and benefits confirmation  
5. **KnowledgeOps**: decisions, requirements traceability, learning, and audit-friendly history  

These practices are designed to be adopted gradually. You can start with a small set of artefacts and routines and expand later.

## How the practices connect

The model works when links are explicit:

- PlanningOps defines the outcomes, scope boundaries, constraints, and delivery sequence  
- BuildOps turns the plan into releasable changes, while keeping risks visible  
- ChangeOps prepares people, operations, and support before each release  
- ValueOps defines what success means and checks it after release  
- KnowledgeOps ensures decisions, requirements, and learnings remain findable and usable  

A simple way to think about it is:

**Outcome → Plan → Work → Release → Adoption → Measurement → Learning**

## Minimum viable ProjectOps

If you want the smallest useful version, use these artefacts and routines for every piece of work:

Artefacts:
- **Project brief** (one page) with outcomes, scope boundaries, and owners
- **Decision log** (start on day one)
- **RAID log** (risks, assumptions, issues, dependencies) with owners
- **Release readiness checklist** (before any go-live)
- **Benefits register** (measures, baselines, owners, review dates)

Routines:
- **Weekly delivery review** (work, blockers, RAID)
- **Fortnightly stakeholder readiness check** (ChangeOps)
- **Monthly outcomes and benefits review** (ValueOps)
- **Post-release review** (what happened, what changed, what to improve)

## Evidence-based delivery

ProjectOps is evidence-led. It prefers light artefacts that stay current:

- what is the outcome and how will we measure it
- what are we delivering and why
- what has been decided and why
- what is blocked and who owns it
- what is ready for release
- what changed in real work and what did we learn
